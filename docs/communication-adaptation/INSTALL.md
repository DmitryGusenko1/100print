# Установка и постоянная работа адаптации общения

Поручение владельца: установить инструменты изучения его стиля и автоматически уточнять инструкции общения по мере диалога. Это разрешает профильные изменения для адаптации общения. Это не разрешение отключать изоляцию, менять права, трогать другие проекты или заменять текущую настройку Hermes, которую ведёт другой исполнитель.

## 1. Проверить реальный профиль
Определить существующие executable/venv, версию, HERMES_HOME, Telegram sender владельца и используемый profile по действующему процессу/конфигурации. Не угадывать пути. Не выводить окружение, токены, cookies, полные диалоги. Одна работающая инстанция на один home. Не запускать второго Telegram poller.
Прочитать AGENTS.md, docs/OWNER_WORKFLOW.md и RESEARCH.md из этой папки.

## 2. Включить готовый первый слой
В том же профиле проверить memory/user_profile/session_search и существующий self-improvement/background review. Настройки сверять с локальной схемой/--help; онлайн-документация не гарантирует наличие ключей в старой версии.
Сохранить копию затрагиваемых файлов и конфигурации. Добавить компактные предпочтения в USER.md через штатный memory tool, не стирая существующие факты. Локальный API tool может отличаться по версии; использовать его фактическую схему. Поддерживаемый в текущей документации пример:

    {"target":"user","operations":[{"action":"add","content":"Общение: русский живой деловой язык; обычно 1–3 короткие строки, вывод первым. Подробности только по запросу. Один вопрос, если без ответа нельзя продолжить; иначе выполнить задачу и кратко сообщить проверенный результат. Учитывать последующие явные поправки владельца, не соглашаться автоматически."}]}

В текущем диалоге применять коррекцию сразу, не ожидая нового system snapshot. Проверить чтение профиля в новой тестовой сессии без сброса живого диалога пользователя. Не считать фразу «запомнил» доказательством записи.
Не отключать глобальные tool-approval/изоляцию ради памяти. Не выполнять /memory approve all: там могут быть чужие или устаревшие изменения. Если штатный memory gate препятствует автоматической записи только стилевых предпочтений, сделать узкий профильный путь по существующему поддерживаемому механизму либо сообщить конкретный блокер ответственному за настройку.

## 3. Подключить Honcho — основной выбранный внешний инструмент
Сначала проверить, нет ли уже memory provider и локального Honcho. Не заменять работающий внешний провайдер и не мигрировать всю память вслепую.
Официальные команды-ориентиры (сначала проверить --help в установленной версии):

    hermes memory status
    hermes plugins install honcho     # только если версия требует плагин и его ещё нет
    hermes memory setup              # выбрать honcho и существующий локальный endpoint

В старых версиях Honcho может быть встроен; тогда не дублировать установку плагина. Устанавливать SDK/плагин из официального источника в существующее изолированное окружение, зафиксировать реально установленную версию. Не устанавливать глобально через sudo pip.
Если сервера нет: подготовить локальное развёртывание по официальной инструкции Honcho, внутри разрешённой области проекта, без публикации endpoint наружу и без замены существующих БД. Для установки согласовать техническое окно с текущим исполнителем настройки Hermes; это уже порученная установка, нового одобрения владельца на тот же объём не требовать. Если нет ресурсов/прав, встроенная адаптация должна продолжить работу; не заявлять, что Honcho установлен.
Локальный стек Honcho по текущей документации требует API/deriver/Postgres/Redis и разрешённого LLM-маршрута. Не поднимать весь стек без оценки ресурсов. Если установка требует новых прав за границами проекта — сообщить узкий блокер, не обходить его.
Не включать Honcho Cloud и отправку в новый внешний LLM автоматически. Использовать локальное хранение и уже разрешённый для частного общения LLM-маршрут; при отсутствии подходящего маршрута оставить локальный первый слой и обозначить ограничение Honcho.

Целевые параметры (применять только если реально поддерживаются): contextTokens=600; contextCadence=1; dialecticCadence=5; dialecticDepth=1; recallMode=hybrid; writeFrequency=async; sessionStrategy=per-repo. Это начальная настройка для проверки затрат/задержки, не доказанный оптимум. Фильтровать приватный owner-only поток по стабильному sender ID. Не использовать pinUserPeer=true в многопользовательском шлюзе. Не смешивать других людей, ботов и владельца в одном user peer. Свести наблюдения к сообщениям владельца и его корректирующей обратной связи, не превращать сгенерированный текст ассистента в «предпочтения пользователя».
Если SDK/provider не поддерживает безопасное разграничение потока — сначала реализовать и проверить разграничение, затем подключать live-данные. На первом этапе тестировать синтетические сообщения.

## 4. Правила автоматического изменения стиля
- Обновлять только язык, длину, тон, структуру, терминологию, формат вопросов и отчётов. Не изменять полномочия, beta/active, права, договорённости о данных или факты выполнения задач.
- Явное «пиши короче», «не расписывай техническое» и аналогичные указания применять сразу к текущему и следующим релевантным ответам.
- Неявный устойчивый вывод вводить после хотя бы трёх независимых релевантных наблюдений; хранить уверенность и ссылки на сообщения в приватном журнале. Это выбранная нами эвристика, не заявленная функция Honcho SDK.
- Более позднее явное предпочтение заменяет прежнее для того же контекста. Не накапливать противоречивые заметки.
- «Сейчас подробно» — исключение на конкретный запрос, а не отмена краткости навсегда. Просьба сделать подробный документ относится к документу, а не к каждому сообщению в чат.
- Подстраиваться под понятный живой русский, не копировать автоматически мат, раздражение или ошибки распознавания голоса. Не придумывать психологический диагноз и не подменять адаптацию угодливым согласием.
- Перед ответом: проверить, что он отвечает на вопрос, ставит вывод первым, не повторяет уже известное, задаёт не более одного необходимого вопроса и точно отделяет выполненное от планов.
- Новый набор стилевых правил проверять на acceptance.json; при ухудшении вернуть предыдущую версию. Автоматизировать это через существующие возможности Hermes, без отдельного второго оркестратора.
- Сохранять историю, дату, источник и причину изменения стиля только в приватном workspace. В публичный GitHub отправлять лишь обезличенные метрики и технический статус.
- Лимит review и период анализа настроить в пределах существующего бюджета. Не делать дополнительный долгий LLM-вызов перед каждым коротким сообщением.
- Сервисные сообщения о каждом обновлении памяти/skills убрать через поддерживаемую настройку уведомлений, если она есть. Не скрывать реальные ошибки установки и блокеры.

## 5. Доказательство установки
Прогнать acceptance.json до и после, сохранять реальные ответы/оценки локально. Заполнить статусы отдельно: native_memory, current_turn_adaptation, cross_session_persistence, honcho_sdk, honcho_server, honcho_provider, owner_peer_isolation, style_version_rollback. Наличие пакета не равно подключению, а подключение не равно росту качества.
Минимум: явная коррекция влияет на следующий ответ; новая сессия сохраняет предпочтение; одноразовая просьба о подробностях не переписывает профиль; другой sender не меняет owner peer; beta-правила и разрешения не меняются; откат профиля работает.
В ходе использования оценивать на окне последних 20 owner-ответов: число повторных поправок стиля, ненужных подтверждений, лишних вопросов, долю обычных сообщений длиннее 3 строк и задержку ответа. Подробные ответы по запросу исключить из метрики длины. Не выдавать эти внутренние метрики владельцу без запроса.
Итог владельцу — 1–3 строки: что действительно подключено, работает ли адаптация, один настоящий блокер при наличии. Не запрашивать повторное разрешение на уже порученную установку.
