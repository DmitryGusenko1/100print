Поручение владельца: [issue #18](https://github.com/DmitryGusenko1/100print/issues/18).
Желаемая структура: [organization.json](../../ops/ai-team/organization.json).
Этот документ описывает целевую конфигурацию. Он не подтверждает установку на VPS.

`reportsTo` в API Paperclip ссылается на AI-агента, не на человека. У Hermes и административного руководителя оно равно `null`; подотчётность human board фиксируется в профилях. Шесть основных руководителей ссылаются на Hermes. Codex ссылается на руководителя производства. Если в установленном релизе доступны штатные команды, использовать их дополнительно, не придумывая отдельную сущность департамента.

Состав сотрудников, модели, подробные скиллы, бюджеты и регулярные рабочие циклы отложены. Самостоятельные предложения новых задач должны проходить согласование владельца. Утверждённый план исполняется без повторных напоминаний. Контроль качества возвращает дефекты на доработку. На данном этапе расписания и автоматические рабочие пробуждения выключены.

## Проверенные официальные исходники

На 7 ноября 2026 года выбраны кандидаты стабильных релизов; совместимость и фактическую установку проверяет исполнитель на VPS:

| Компонент | Кандидат / требование | Официальный источник |
|---|---|---|
| Paperclip | `v2026.1106.0` | [Release](https://github.com/paperclipai/paperclip/releases/tag/v2026.1106.0) |
| Node.js для этого Paperclip | `>=24.11.0`; устанавливать отдельно от runtime сайта | [package.json](https://github.com/paperclipai/paperclip/blob/v2026.1106.0/package.json) |
| pnpm | `9.15.4` в packageManager релиза | [package.json](https://github.com/paperclipai/paperclip/blob/v2026.1106.0/package.json) |
| Hermes Agent | `v0.23.0` | [Release](https://github.com/NousResearch/hermes-agent/releases/tag/v0.23.0) |
| Codex CLI | Сначала проверить существующую версию и авторизацию | [Адаптер Codex](https://github.com/paperclipai/paperclip/blob/v2026.1106.0/docs/adapters/codex-local.md) |

Нельзя выдавать эти кандидаты за установленные версии. Записывать точные версии бинарных файлов, commit/digest и результат проверки на VPS в отчёт приёмки.

Paperclip включает `hermes_local` и `hermes_gateway` [штатно](https://github.com/paperclipai/paperclip/blob/v2026.1106.0/packages/adapters/hermes/README.md). Для одного VPS предпочтителен `hermes_local`: Paperclip запускает CLI на ограниченную задачу и сохраняет сессию. Отдельный постоянно работающий Hermes gateway для этого варианта не требуется. Не создавать фиктивный сервис с бесконечным ожиданием. Если выбран `hermes_gateway`, использовать настоящий штатный API-сервер, отдельный ключ доступа и loopback.

Для Codex использовать штатный `codex_local` либо поддержанный закреплённым релизом Runner. Сначала проверить существующую авторизацию под тем же разрешённым Linux-пользователем. Не публиковать credential values и не заменять авторизацию действующего исполнителя.

## Развёртывание и хранение

1. Снять состояние ресурсов, версий, служб и портов до изменений. Записывать имена процессов без командных строк, способных содержать секреты.
2. Изолировать новые приложения и данные в `/opt/ceo-orchestrator/ai-team/`. Не менять сайт, базы других проектов, действующие боты, webhook и nginx. Новые units именовать `ceo-ai-team-*`.
3. Назначить постоянные `PAPERCLIP_HOME`, `PAPERCLIP_INSTANCE_ID`, `HERMES_HOME`, storage и БД. Не хранить их в checkout или `/tmp`. Использовать отдельный конфиг и ключ шифрования с правами `0600`, каталоги `0700`.
4. До старта проверить свободные порты; не выбирать порт по предположению. Panel bind: loopback. Режим Paperclip: `authenticated` + `private`. `local_trusted` не подтверждает требование авторизованного доступа.
5. Настроить systemd, `Restart=on-failure`/`always`, журналы journald и ограничение их роста. Привязать startup к постоянным путям. Не перезапускать действующий сайт и ботов.
6. Bootstrap владельца выполнять штатным способом. Claim URL, cookies, API-ключи, секреты шифрования и пароли не включать в GitHub или отчёт. Если требуется действие человека, передать одно конкретное действие через защищённый доступ к панели.

После проверки loopback-порта доступ к панели открывается SSH-туннелем с компьютера владельца. Реальные порт и URL необходимо записать в отчёт; данный документ не объявляет панель доступной.

## Backup и восстановление

Исполнитель должен подготовить рабочую команду резервного копирования с учётом реального способа установки. Для встроенной БД использовать штатный database backup либо согласованную остановку только нового сервиса. Для внешнего PostgreSQL использовать согласованный `pg_dump`, не копирование живых data files.

Одна резервная точка включает БД Paperclip, attachments/storage, конфигурацию и ключи шифрования, Hermes home с памятью и историей, runtime state и версии приложений. Учитывать SQLite WAL: применять SQLite backup API или остановку пишущего процесса перед копированием. Секреты нужны для восстановления, но не для публичного отчёта.

Хранить копии вне git с `0700/0600`, записывать контрольные суммы, timestamp, список включённых данных без их содержимого. Локальная копия не защищает от потери всего VPS; внешний destination требует отдельной настройки и не должен объявляться существующим.

Проверка восстановления: восстановить копию в новый каталог/отдельную БД на свободном loopback-порту; выключить wake/cron/исполнителей; проверить компанию, структуру, task history и тестовый результат. Не восстанавливать поверх рабочего экземпляра для испытания. Зафиксировать фактические команды в эксплуатационном runbook.

## Приёмка

| Проверка | Минимальное свидетельство |
|---|---|
| Создание | Реальные company/project/agent IDs, семь профилей руководителей, структура подчинения |
| Подключение | Успешная проверка adapter environment, путь CLI, версия, наличие рабочей авторизации без её содержимого |
| Выполнение | Тестовый task/run ID, назначение, реальный файл-результат в sandbox, возврат результата, сохранённый статус |
| Hermes | Отдельный успешный bounded run через штатный адаптер |
| Codex | Отдельный успешный bounded run через штатный адаптер |
| QA | Возврат неудовлетворительного результата, исправление и повторная приёмка тестовой задачи |
| Согласование | Native approval ID, pending; попытка AI самосогласования отклонена; задача не выполняется до разрешения |
| Решение владельца | Реальное действие владельца либо явная пометка, что полная положительная проверка ещё не выполнена |
| Перезапуск | enabled/active новых units; прежние entity IDs, история и результат доступны после рестарта |
| Восстановление | Отдельное восстановленное окружение, выключенные исполнители, проверенные данные |
| Сохранность окружения | Состояние сайта и действующих ботов до/после; не выдавать HTTP-проверку сайта за Telegram E2E |

`approve_ceo_strategy` — штатный тип approval, но наличие pending-записи само по себе не доказывает блокировку любой задачи. Проверить реальное поведение поддерживаемой связки approval/tasks. Не утверждать за Дмитрия и не маскировать текстовый регламент под техническую блокировку.

Формат итогового отчёта: точные версии, новые services и способы диагностики, фактический URL и вход, CREATED / CONNECTED / VERIFIED для каждого профиля/исполнителя, результаты проверок, commit SHA и оставшиеся блокеры. Exit code 0, запись профиля или создание issue не означают готовность инфраструктуры.
